# Admin Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create a completely separate administrator identity system where this device becomes the root trust device, every login proves possession of an approved non-exportable P-256 key, new devices wait for root approval, and one-time recovery codes can replace a lost root.

**Architecture:** Store admin users, devices, requests, one-use challenges, hashed sessions, recovery codes, bootstrap codes, and append-only audit events in dedicated tables. The browser signs canonical one-use challenges; Node verifies WebCrypto P-256 signatures. A hidden-terminal CLI creates the sole admin user and prints bootstrap/recovery material once, but real initialization waits until the Phase 6 browser UI exists.

**Tech Stack:** Node `crypto`, `bcryptjs` cost 12, PostgreSQL, Express, WebCrypto ECDSA P-256, IndexedDB in Phase 6, secure cookies, existing PostgreSQL rate limiter.

## Global Constraints

- No ordinary `users` row, App JWT, `ADMIN_EMAILS`, or consumer session grants admin access.
- Admin username and password are separate from every consumer account.
- Password hashes use bcrypt cost 12.
- The password never appears in command arguments, shell history, logs, audit payloads, or Git.
- Device private keys are non-exportable and never leave browser storage.
- Approved-device login requires password plus a signature over a server one-time challenge.
- New-device password success creates only a pending request, not a session.
- Only the root device can approve or reject new devices in version 1.
- Recovery requires password plus one unused recovery code, registers a new root, and revokes every old device and session.
- Ten recovery codes are generated, shown once, and stored only as hashes server-side.
- Session cookie is `HttpOnly; Secure; SameSite=Strict`; CSRF token is a separate Secure Strict cookie and matching header.
- Idle expiry is 30 minutes; absolute expiry is eight hours.
- Admin API has no CORS headers and the web console loads no third-party scripts.

- [x] **Step 2: Implement canonical bytes and verification**

```js
import { createHash, createPublicKey, verify } from "node:crypto";

export function canonicalChallengePayload({ challengeId, purpose, nonce, targetId = "" }) {
  return Buffer.from(["zbt-admin-v1", challengeId, purpose, nonce, targetId].join("\n"), "utf8");
}

export function publicKeyFingerprint(jwk) {
  const canonical = JSON.stringify({ crv: jwk.crv, kty: jwk.kty, x: jwk.x, y: jwk.y });
  return createHash("sha256").update(canonical).digest("hex");
}

export function verifyDeviceSignature({ publicKeyJwk, payload, signature }) {
  try {
    const key = createPublicKey({ key: publicKeyJwk, format: "jwk" });
    return verify("sha256", payload, { key, dsaEncoding: "ieee-p1363" }, Buffer.from(signature, "base64url"));
  } catch {
    return false;
  }
}
```

Reject JWKs unless `kty='EC'`, `crv='P-256'`, `key_ops` is absent or includes `verify`, and `x/y` decode to 32 bytes.

- [x] **Step 1: Write the complete failing lifecycle test**

Use generated Node P-256 pairs and real HTTP calls to prove:

```text
bootstrap code + correct password enrolls first root
bootstrap code cannot be reused

root-signed approval creates an approved non-root device
non-root approval returns 403
```

- [x] **Step 2: Implement password verification and lockout**

Normalize username, use the same generic error for unknown username and bad password, apply PostgreSQL rate limits by IP+username, and lock for 15 minutes after ten consecutive failures. Successful approved login resets the counter.

- [x] **Step 3: Implement root bootstrap and pending requests**

`POST /device-requests` accepts `{ username, password, deviceID, displayName, publicKeyJWK, bootstrapCode? }`.

- With a valid unused bootstrap code and no approved device: create the root immediately, consume the code, audit `admin.root_enrolled`.
- Without bootstrap: verify password, create/update a ten-minute pending request, return request ID and six-character short code, audit `admin.device_requested`, and set no cookies.

Hash source IP and short code; store only a coarse browser/OS user-agent summary capped at 120 characters.

- [x] **Step 4: Implement challenge login**

`POST /auth/challenges` creates a login challenge only for an approved device ID and normalized username. `POST /auth/login` verifies password, consumes challenge, verifies signature against that device JWK, creates the session cookies, updates device use time, and audits success/failure without signatures or nonce.

`GET /auth/session` returns only the authenticated admin ID/username, current device ID/name/root flag, and session expiry metadata. `GET /auth/devices` and `GET /auth/device-requests` require an authenticated root session and return no key coordinates, hashes, IP hashes, or session tokens.

- [x] **Step 5: Implement signed root approval/rejection**

The root session first requests an `approve_device` or `reject_device` challenge tied to the request ID. The decision endpoint requires session, CSRF, root status, challenge, signature, and matching short code confirmation. Approval copies the pending JWK into `admin_devices`; rejection preserves only audit metadata.

- [x] **Step 6: Implement recovery**

`POST /auth/recover` rate-limits aggressively, verifies username/password/recovery code in one locked transaction, marks code used, revokes all sessions/devices, creates the supplied new P-256 device as root, and audits `admin.root_recovered`. It never returns old device information before success.

- [x] **Step 7: Mount admin API before global CORS**

In `app.js`, mount `/admin/api` before `app.use(cors())`. Apply JSON size limit 256 KB, no CORS headers, `Cache-Control: no-store`, and the existing error shape with stable admin error codes. Keep consumer `/api` unchanged.
