**R03｜验证码的“最多 5 次错误”实际上不会累计**

**R04｜数据库限流有两处独立错误**

[限流 SQL](/Users/rudy2009/Documents/欧美团app/backend/src/rateLimit.js:51)使用同一语句内的 INSERT CTE 和表计数，主查询读到的是不包含本次新增行的快照，判断条件又是 `> max`。在真实 PostgreSQL 设置 max=3，前四次均通过，第五次才 429。并发请求还可能在相同历史计数上同时通过，本次没有把并发穿透程度量化。

更严重的是 [清理逻辑](/Users/rudy2009/Documents/欧美团app/backend/src/rateLimit.js:80)：每个限流器按自己的 `windowSeconds * 2` 清理整张表，却不区分 scope。一分钟窗口的邮件/资源限流会删除超过两分钟的登录记录，而登录窗口是十五分钟。复现中，一条仅三分钟前产生、仍应被登录限流计入的记录被删除。

建议：选择能够原子判断和更新的限流模型；清理按 scope 对应保留期处理，或全表保留期不低于最长窗口。核对 Nginx 与 Express 的代理 IP 设置，否则资源限流可能把多个用户算作同一个代理 IP；本次未读取生产代理配置。

验收：max=3 时第四次拒绝；并发测试不突破承诺上限；短窗口清理不破坏长窗口。

**R09｜同步游标把“ID 分配顺序”误当成“事务提交顺序”**

[sync_events](/Users/rudy2009/Documents/欧美团app/backend/sql/005_sync_events.sql:1)使用 bigserial。[同步读取](/Users/rudy2009/Documents/欧美团app/backend/src/sync.js:39)按 `id > cursor` 获取，游标推进到已读最大 ID。

真实数据库复现：事务 A 分到事件 11 尚未提交；事务 B 分到事件 12 并先提交；客户端读到 12，保存 cursor=12；A 随后提交 11，下一次查询永久跳过 11。结果记录中的 `afterLateCommitEvents=0`。

这会造成偶发漏消息、漏状态。WebSocket 的“有变化”提醒仍触发同一个游标查询，不能恢复已经跳过的较小 ID。另一个缺口是事件七天清理后，服务端没有返回“游标过旧，请全量重建”的协议。

建议：让事件的可见顺序与游标语义一致，例如按用户串行化事件分配与提交，或使用提交后分发机制；再增加客户端幂等处理、过旧游标重建及跨事务乱序测试。不要仅把 LIMIT 调大当作修复。

验收：稳定复现上述两事务顺序且不丢事件；离线超过保留期能恢复完整状态；重复事件不造成重复消息。

**R10｜旧网络响应可能把退出或切换后的账号状态覆盖回来**

[refreshFromBackend](/Users/rudy2009/Documents/欧美团app/ZhouBianTuan/MockAppStore.swift:336)和 sync 在 await 前读取 token，返回后直接写全局 store，没有再次验证账号、token 或 `authSessionVersion`。[退出](/Users/rudy2009/Documents/欧美团app/ZhouBianTuan/MockAppStore.swift:1448)虽然清空状态，但只取消自动刷新任务与 WebSocket，没有统一取消已有 bootstrap、同步和写入 Task。

因此 A 账号请求在途时退出、或再登录 B，A 的旧响应可能恢复 A 的资料、把 `isLoggedIn` 设回 true，或把同步游标写到当前账号的 key。此项依据明确调用链提出；本次没有在客户端用延迟网络实测，不能断言已经在用户设备发生。

建议：每次请求绑定会话版本；写回前检查版本一致；退出/切换统一取消所属请求，并忽略过期回调。WebSocket 断连回调也应检查是否仍属于当前连接。

验收：人为延迟 A 的 bootstrap/sync，切换到 B，再释放 A 响应；界面、游标、消息和登录状态始终属于 B。

**R11｜发布失败会丢掉刚填写的表单**

[发布按钮](/Users/rudy2009/Documents/欧美团app/ZhouBianTuan/CreatePostViews.swift:289)调用同步返回的 `store.createPost` 后立刻 `reset()` 或 dismiss。[store 的真正上传和发帖](/Users/rudy2009/Documents/欧美团app/ZhouBianTuan/MockAppStore.swift:2245)在内部 Task 执行，因此重置发生在上传/审核完成之前。

网络失败、图片上传失败或超时时，最终只留下 toast，用户刚写的内容和图片选择已被清空。没有明确的 publishing 状态，也没有把可恢复草稿和发布任务绑定。每次 createPost 生成新 ID，用户重试还可能在上一次请求实际成功但响应超时的情况下发出重复帖子。

建议：让发布返回可等待的结果；成功后再清空，失败保持草稿；禁止同一个发布任务重复提交；给一次发布稳定的幂等标识。超时状态要允许查询结果后再重试。

验收：在上传、审核和响应三个阶段分别断网；草稿保留，状态可解释，恢复重试不重复发帖。

**R12｜拼谷库存编辑和部分合集操作没有保存到后端**

[角色新增、修改、删除](/Users/rudy2009/Documents/欧美团app/ZhouBianTuan/MockAppStore.swift:2181)只改 `posts[index].unsoldRoles`，没有 API 调用；[详情页](/Users/rudy2009/Documents/欧美团app/ZhouBianTuan/PostDetailViews.swift:850)确实提供相应编辑入口。换设备、重新加载或重启后会恢复旧库存，其他买家和搜索也看不到更新。

[addPost/removePost](/Users/rudy2009/Documents/欧美团app/ZhouBianTuan/MockAppStore.swift:2136)同样是本地操作。此外客户端提示帖子必须保留在一个合集里，但后端删合集使用硬删除，外键 `ON DELETE SET NULL` 会留下没有合集的帖子。需要确认这一业务规则，而不是只维持矛盾提示。

建议：为库存和合集归属补受作者权限保护的更新接口，校验数量、价格和并发版本，成功后同步给其他用户。库存是社区交易信息可信度的一部分，应优先于视觉细修。

验收：A 修改库存，B 搜索和查看详情能看到新值；A 重启后不恢复旧值；并发编辑不会无提示覆盖。

**R13｜数据条数上限已经造成正确性问题**

[bootstrap](/Users/rudy2009/Documents/欧美团app/backend/src/bootstrap.js:5)取全站最近 200 帖、200 合集、500 评论、100 会话和合计 500 条消息；并不是每个页面各自分页。客户端搜索、我的帖子和收藏主要过滤这份本地列表。

建议：按首页、作者主页、收藏、合集、评论、会话分别提供游标分页；搜索走服务端；共享帖子支持按 ID 补取详情与作者。保留 limit 保护是正确的，但必须提供继续加载路径。不能仅把 200 改成 2000。

验收：201+ 帖子、500+ 评论、100+ 会话和长聊天数据下，旧收藏与历史内容仍可逐页获取，没有全站其他用户的数据把当前用户历史挤掉的现象。

**R14｜数据库异常可能造成请求挂起或进程退出**

[health](/Users/rudy2009/Documents/欧美团app/backend/src/routes.js:54)和 [bootstrap](/Users/rudy2009/Documents/欧美团app/backend/src/routes.js:187)是没有 try/catch 的 async handler。当前锁定 Express 4.22.2，不具备 Express 5 的自动 Promise rejection 转交逻辑。版本差异可见 [Express 官方迁移说明](https://expressjs.com/en/guide/migrating-5/)。

隔离测试把数据库 query 替换为拒绝的 Promise，访问 health 观察到未处理拒绝，HTTP 请求超时而不是 5xx。本诊断进程临时监听 unhandledRejection 才保留下来；生产是否退出取决于 Node 运行方式和全局监听，不能只用一次健康 200 排除这项风险。

[错误处理器](/Users/rudy2009/Documents/欧美团app/backend/src/app.js:22)还把内部 `error.message` 原样返回，数据库/上游内部信息可能出现在客户端。数据库鉴权查询的异常在 [requireAuth](/Users/rudy2009/Documents/欧美团app/backend/src/auth.js:27)又被统一转成 401，数据库故障可能表现为用户被要求重新登录。

建议：统一 async handler 错误转交；服务错误与凭据失效分开；5xx 返回稳定的用户提示，详细信息写带请求 ID 的内部日志。补数据库超时、连接池错误处理和受控停机。

验收：数据库断开时 health/bootstrap 稳定返回 503，进程可恢复，客户端不因数据库故障清除有效登录。

**R15｜上传和云审核成本缺少服务端上限**

[上传签名](/Users/rudy2009/Documents/欧美团app/backend/src/routes.js:1143)仅校验声明的 MIME，没有次数、字节数、用户配额、实际文件内容核验与完成确认。[签名生成](/Users/rudy2009/Documents/欧美团app/backend/src/oss.js:46)返回十五分钟 PUT 权限，没有禁止覆盖已上传对象的参数。后端对帖子的图片数组也未限定数量，审核按所有图片并发发请求。

`express.json` 的 2MB 限制不限制客户端直传 OSS 的图片体积。攻击者能反复申请签名上传孤儿文件，或构造许多对象键造成审核成本。签名在有效期内是否能覆盖已审核对象、Bucket 是否有额外策略，需要云配置验收；源码中没有保证对象审核后不可变。

建议：服务端统一字段/数组长度限制；上传配额和短期票据；校验文件真实格式、大小与尺寸；审核前后绑定对象版本/哈希；正式发布对象禁止覆盖。使用后台队列、并发限制、超时、失败重试与费用预算。补未引用资源的定期清理任务。

验收：超大文件、图片过多、重复签名、已审对象替换均被可靠限制；失败重试可恢复且不会重复计费。实际 OSS 和供应商测试应在明确费用授权后执行。

**R16｜实时机制仍依赖每三秒轮询**

[runFallbackSyncIfNeeded](/Users/rudy2009/Documents/欧美团app/ZhouBianTuan/MockAppStore.swift:417)只检查最近一次业务事件距今是否超过三秒，不因为 WebSocket 已连接就停止轮询。安静时会持续请求 sync。即使没有事件，[sync](/Users/rudy2009/Documents/欧美团app/backend/src/sync.js:39)仍查询未读数与整套关系表。

按代码估算，1000 个前台空闲客户端约产生 333 次 sync/秒；每次无事件至少约 8 次数据库查询，约 2667 次查询/秒。这是数量级推算，不是容量压测结果，也不代表当前已经有这样的用户量。

[服务端连接表](/Users/rudy2009/Documents/欧美团app/backend/src/realtime.js:8)仅在进程内，未来多进程的通知不能天然互通；鉴权只在握手执行，未见定时重验、账号删除时踢连接、单账号连接数限制或发送缓冲保护。客户端在 `resume()` 后立即标记 connected，也没有等握手成功。

建议：健康连接主要依靠事件与低频校验，断连时采用带随机抖动的退避轮询；真正测量握手和断连；为账号失效、连接数、缓冲区和多实例分发建立约束。现阶段可保留单体部署，不必因此立即引入复杂消息系统。

**R17｜私信“增量”更新和本地持久化仍是全量操作**

[loadMessageThreadForUser](/Users/rudy2009/Documents/欧美团app/backend/src/messages.js:3)每次读完整个会话所有消息；一个已读事件也返回整段历史。真实复现中，600 条消息的会话产生一个 read 事件，sync 回传了 600 条消息。多会话逐个查询还会扩大查询数量。

建议：服务端同步新消息、变更状态和 tombstone，历史另行分页；本地消息结构化存储或增量落盘，把文件工作移出主线程并合并重复写入；图片数据与消息元数据分离。为新收到的陌生发送者补齐用户资料，避免 `user(id:)` 缺失时退回“当前用户”而显示错误头像昵称。

验收：一条新消息或 read 事件的传输量不随全部聊天历史线性增长；大历史数据下发送和滚动保持顺畅，后台存储失败可观察。
