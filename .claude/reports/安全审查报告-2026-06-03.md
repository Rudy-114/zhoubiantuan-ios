## P0 - 严重安全/隐私风险

### P0-1: `/feed` 未认证接口泄露所有用户邮箱

**文件:** `backend/src/routes.js:302`  
**关联文件:** `backend/src/mappers.js:3-28`

**现象:** `/api/feed` 接口无需认证即可访问，但查询 users 表并通过 `userToClient()` 返回完整 User 对象，包含 `email` 字段。

**风险:** 任何人无需登录即可通过 `/api/feed` 爬取所有注册用户邮箱，属于严重隐私泄露。在欧盟 GDPR 和中国《个人信息保护法》下均属于违规。

**建议修法:**

```js
// mappers.js - userToClient 增加 viewerUserId 参数
export function userToClient(row, counts = {}, viewerUserId = "") {
  const isSelf = viewerUserId && viewerUserId === row.id;
  return {
    // ...
    email: isSelf ? (row.email || "") : "",  // 仅本人可见
    // ...
  };
}

// routes.js - /feed 调用时传空 viewerUserId
users: usersResult.rows.map((row) => userToClient(row, row, ""))
```

**是否需要用户决策:** 否，直接修。

### P0-2: JWT 密钥有硬编码开发默认值

**文件:** `backend/src/config.js:24`

**现象:**

```js
jwtSecret: process.env.JWT_SECRET || "dev-only-change-before-beta"
```

如果生产环境忘记设置 `JWT_SECRET` 环境变量，系统会静默使用 `"dev-only-change-before-beta"` 签发和验证所有 token。

**风险:** 攻击者可以使用这个已知密钥伪造任意用户的 JWT token，完全绕过认证系统，以任意用户身份操作。

**建议修法:**

```js
// config.js - 去掉默认值，强制要求配置
function required(name) {
  const value = process.env[name];
  if (!value) {
    throw new Error(`Missing required environment variable ${name}`);
  }
  return value;
}

// 使用
jwtSecret: required("JWT_SECRET"),
```

**是否需要用户决策:** 否，直接修。

### P0-3: 邮箱验证码哈希密钥回退到 JWT_SECRET

**文件:** `backend/src/config.js:57`

**现象:**

```js
codeSecret: process.env.EMAIL_CODE_SECRET || process.env.JWT_SECRET || "dev-only-email-code-secret"
```

如果未配置独立的 `EMAIL_CODE_SECRET`，会逐级回退到 `JWT_SECRET`，最终到硬编码字符串。

**风险:** 如果 JWT_SECRET 泄露（如在日志中意外输出），攻击者不仅能伪造 token，还能对 6 位验证码进行离线暴力破解（SHA256 hash 在已知密钥下 millisecond 级别可暴破 100 万种组合）。验证码形同虚设。

**建议修法:**

```js
codeSecret: process.env.EMAIL_CODE_SECRET 
  || required("EMAIL_CODE_SECRET")  // 强制要求独立配置
```

或者在启动时自动生成并仅在当前进程生命周期内有效（重启后所有验证码失效，可接受）。

**是否需要用户决策:** 否，直接修。

## P1 - 高风险问题

### P1-1: Bootstrap 启动全量加载所有数据

**文件:** `backend/src/bootstrap.js:5-81`

**现象:** 每次登录/启动时，`loadBootstrap` 执行 11 个并行查询：

1. `SELECT * FROM users` —— 所有用户
2. `SELECT * FROM posts` —— 所有帖子（带 4 个子查询）
3. `SELECT * FROM group_collections` —— 所有合集（带 LEFT JOIN posts）
4. `SELECT * FROM comments` —— 所有评论（带子查询）
5. `SELECT * FROM reports LIMIT 100`
6. `SELECT * FROM post_likes WHERE user_id = $1` —— 本人点赞
7. `SELECT * FROM post_favorites WHERE user_id = $1` —— 本人收藏
8. `SELECT * FROM follows WHERE follower_id = $1` —— 本人关注
9. `SELECT * FROM follows` —— **全表所有关注关系**
10. `SELECT * FROM message_threads` —— 本人会话（带子查询 unread_count）
11. `SELECT * FROM direct_messages` —— **本人所有历史消息**

**风险:**
- 全表 `SELECT * FROM follows` 在 1000 用户/10000 关注时可达数 MB
- 全量消息查询在长期用户下可能返回数十万条
- 所有数据加载阻塞登录流程，弱网环境分钟级超时
- 服务端内存压力随用户量线性增长

**建议修法:**

1. **follows 全表查询（最严重）:** 改为只查与当前用户相关的关注关系（当前用户关注的人 + 关注当前用户的人），不要返回所有用户的关注关系。

```js
// bootstrap.js 替代 follows 全表查询
query(
  `SELECT follower_id, following_id FROM follows 
   WHERE follower_id = $1 OR following_id = $1`, 
  [userId]
)
```

2. **posts 加分页:** 最近 200 条而非全部。
3. **messages 加限制:** 最近 200 条而非全部历史。
4. **comments 加限制:** 最近 500 条。

**是否需要用户决策:** 建议在用户量达到 500+ 前处理。

### P1-2: 每个帖子查询嵌入 4 个 count 子查询 (N+1 问题)

**文件:** 
- `backend/src/routes.js:305-310` (feed)
- `backend/src/sync.js:143-148` (sync)
- `backend/src/bootstrap.js:16-20` (bootstrap)

**现象:** 查询每个帖子时，SELECT 中嵌入 4 个关联子查询：

```sql
SELECT p.*,
  (SELECT count(*) FROM post_likes l WHERE l.post_id = p.id) AS liked_count,
  (SELECT count(*) FROM post_favorites f WHERE f.post_id = p.id) AS favorite_count,
  (SELECT count(*) FROM comments c WHERE c.post_id = p.id AND c.status = 'active') AS comment_count,
  (SELECT count(*) FROM reports r WHERE r.target_type = 'post' AND r.target_id = p.id) AS report_count
FROM posts p
```

**风险:** 假设返回 40 条帖子，每条 4 次子查询 = 160 次额外索引扫描。随着帖子量增加，每次查询开销线性增长。

**建议修法:**

方案 A（推荐，简单改动）: 用 LEFT JOIN + GROUP BY 替代子查询：

```sql
SELECT p.*,
  COALESCE(l.cnt, 0) AS liked_count,
  COALESCE(f.cnt, 0) AS favorite_count,
  COALESCE(c.cnt, 0) AS comment_count,
  COALESCE(r.cnt, 0) AS report_count
FROM posts p
LEFT JOIN (SELECT post_id, count(*) AS cnt FROM post_likes GROUP BY post_id) l ON l.post_id = p.id
LEFT JOIN (SELECT post_id, count(*) AS cnt FROM post_favorites GROUP BY post_id) f ON f.post_id = p.id
LEFT JOIN (SELECT post_id, count(*) AS cnt FROM comments WHERE status = 'active' GROUP BY post_id) c ON c.post_id = p.id
LEFT JOIN (SELECT target_id, count(*) AS cnt FROM reports WHERE target_type = 'post' GROUP BY target_id) r ON r.target_id = p.id
WHERE p.status = 'active'
ORDER BY p.created_at DESC
LIMIT $1
```

方案 B: 定期用物化视图刷新计数（适合更后期）。

**是否需要用户决策:** 否。

### P1-3: 公开内容 sync 事件广播给全体用户

**文件:** 
- `backend/src/routes.js:1114-1121` (syncAudienceForPublicContent)
- `backend/src/routes.js:494-501` (发帖 sync)
- `backend/src/routes.js:1137-1143` (点赞 sync)

**现象:**

```js
async function syncAudienceForPublicContent(client, seedUserIds, shouldBroadcast) {
  if (shouldBroadcast) return activeUserIds(client);  // <-- 返回所有用户
  return uniqueIds(seedUserIds);
}
```

当帖子审核通过（status="active"）后，点赞/收藏/评论等操作都会向**所有活跃用户**写入 sync_events。此外，`setPostReaction` 的 audience 始终是 `activeUserIds(client)`，不受 `shouldBroadcast` 控制。

**风险:**
- 10000 用户 × 每次点赞 = 10000 条 sync_events 写入
- sync_events 表极速膨胀
- 每个用户的 `/sync` 轮询会拉取大量不相关事件
- 数据库写入和存储成本线性增长

**建议修法:**

对于公开内容的互动（点赞/收藏数变化），不需要实时广播给所有用户。客户端在打开帖子详情时重新拉取即可。

1. `setPostReaction` 的 audience 改为只通知帖子和互动双方：

```js
const audience = uniqueIds([userId, post.rows[0].author_id]);
```

2. 评论的通知范围改为帖主 + 被回复者 + 评论者。
3. `syncAudienceForPublicContent` 在 `shouldBroadcast=true` 时改为只通知活跃用户的子集（如最近 7 天登录的），或直接废弃 broadcast 模式。

**是否需要用户决策:** 是——这涉及产品决策：哪些内容更新需要实时推送给所有用户。

### P1-4: JWT Token 在 UserDefaults 中明文存储

**文件:** `ZhouBianTuan/MockAppStore.swift:89-100`

**现象:**

```swift
var backendToken: String? {
    get {
        cachedBackendToken ??
        KeychainStore.string(forKey: Self.backendTokenDefaultsKey) ??
        UserDefaults.standard.string(forKey: Self.backendTokenFallbackDefaultsKey)  // 明文
    }
    set {
        if let newValue, !newValue.isEmpty {
            cachedBackendToken = newValue
            KeychainStore.set(newValue, forKey: Self.backendTokenDefaultsKey)
            UserDefaults.standard.set(newValue, forKey: Self.backendTokenFallbackDefaultsKey)  // 明文
        }
        // ...
    }
}
```

Token 同时存储到 Keychain 和 UserDefaults。UserDefaults 底层是 plist 明文文件，设备越狱或 iTunes 备份后可被直接读取。

**风险:** JWT token 泄露可被用于冒充用户。30 天有效期的 token 一旦泄露，攻击者有长达 30 天的窗口期。

**建议修法:** 移除 UserDefaults fallback。如果 Keychain 写入失败，应当视为错误而非降级存储：

```swift
set {
    if let newValue, !newValue.isEmpty {
        cachedBackendToken = newValue
        if !KeychainStore.set(newValue, forKey: Self.backendTokenDefaultsKey) {
            // Keychain 写入失败，不降级到 UserDefaults
            showToast("安全存储异常，请重试")
            return
        }
    }
    // ...
}
```

**是否需要用户决策:** 否。

### P1-5: 图片代理端点 `/api/assets/*` 可被滥用

**文件:** `backend/src/routes.js:39-57`

**现象:** `/api/assets/*` 接受路径后通过 OSS signed URL 代理图片。虽然做了前缀检查和 `..` 过滤，但：
- 没有针对此端点的独立限流
- 设置了 `Cache-Control: public, max-age=2592000, immutable`（30 天），但这是客户端缓存，ECS 每次仍需代理
- 每条请求都会生成新的 OSS signed URL

**风险:**
- 恶意用户用大量并发请求刷图片代理端点，消耗 ECS 出带宽和 OSS 签名配额
- 在 CDN 正式接入前，所有图片流量都经过 ECS

**建议修法:**

1. 对这个端点加独立 rate limiter：

```js
const assetLimiter = createRateLimiter({
  windowMs: 60 * 1000,
  max: 120,
  message: "请求太频繁",
  keyGenerator: (req) => req.ip
});
router.get("/assets/*", assetLimiter, async (req, res, next) => { ... });
```

2. 添加 OSS signed URL 内存缓存（如 LRU cache 60 秒），相同 objectKey 在有效期内复用已签名的 URL。
3. CDN 正式接入后，`publicAssetUrl` 直接返回 CDN URL 而非代理，此端点仅作 fallback。

**是否需要用户决策:** 否。

### P1-6: 审核失败模式 fallback 不完整

**文件:** 
- `backend/src/config.js:43-44`
- `backend/src/moderation/index.js:84-98`

**现象:**

```js
failMode: process.env.MODERATION_FAIL_MODE || "review"
```

`safeReview` 中：

```js
async function safeReview(callback, source) {
  try {
    return await callback();
  } catch (error) {
    if (config.moderation.failMode === "block") {
      return normalizeModerationResult({ outcome: "block", ... });
    }
    return moderationErrorResult(error, source);  // 默认进 review
  }
}
```

当前行为：阿里云审核 API 超时/失败时，内容默认进入人工审核而非直接活跃（failMode 非 "block" 时走 else 分支 = review）。这个行为是正确的。

但 failMode 配置值如果被错误设置为空字符串或其他值，会走 else 分支进 review（安全）。风险较低。

**风险:** 低——当前逻辑已正确。failMode="block" 会导致审核故障时所有内容无法发布（过于严格）。建议保持现状。

**建议修法:** 在 `safeReview` 中加显式注释说明 failMode 逻辑，避免后续维护误解。可选：failMode 增加枚举校验。

**是否需要用户决策:** 否。

## P2 - 中风险问题

### P2-1: 内存限流器不支持多实例部署

**文件:** `backend/src/rateLimit.js:2-26`

**现象:** 限流使用内存 `Map` 存储。在多进程（cluster mode）或多 ECS 实例部署时，各实例独立计数，限流失效。

```js
const buckets = new Map();  // 仅当前进程
```

此外，虽在 10000 条时触发清理，但清理逻辑只在有新请求时才执行，高频攻击下可能短时间爆炸。

**风险:** 水平扩展时登录/验证码限流失效。单实例内存可能因高频攻击增长。

**建议修法:** 生产环境换用 Redis 限流（如 `rate-limit-redis` + ioredis）。当前单实例可用，水平扩展前需处理。

**是否需要用户决策:** 在水平扩展前处理即可。

### P2-2: 举报不验证目标是否存在

**文件:** `backend/src/routes.js:915-930`

**现象:** 创建举报时直接 INSERT，不检查 `targetId` 对应的帖子或评论是否真实存在：

```js
router.post("/reports", requireAuth, async (req, res, next) => {
  const targetType = req.body.targetType === "comment" ? "comment" : "post";
```

**风险:** 攻击者可以用不存在的 targetId 大量刷举报记录，污染举报表。

**建议修法:**

```js
// 插入前查询目标
if (targetType === "post") {
  const post = await query("SELECT id FROM posts WHERE id = $1", [targetId]);
  if (!post.rows[0]) throw badRequest("举报的帖子不存在");
} else {
  const comment = await query("SELECT id FROM comments WHERE id = $1", [targetId]);
  if (!comment.rows[0]) throw badRequest("举报的评论不存在");
}
```

**是否需要用户决策:** 否。

### P2-3: WebSocket 认证 token 可通过 URL 参数传递

**文件:** `backend/src/realtime.js:120-124`

**现象:**

```js
function tokenFromRequest(request, url) {
  const header = request.headers.authorization || "";
  const [, headerToken] = header.match(/^Bearer\s+(.+)$/i) || [];
  return headerToken || url.searchParams.get("token") || "";  // URL 参数
```

Token 可通过 WebSocket URL 的 query string 传递（如 `wss://api.xxx/api/ws?token=xxx`）。

- 服务器 access log
- 浏览器/WebView 历史记录
- 中间网络设备日志

**建议修法:** 移除 URL query param 方式，只接受 `Authorization` header（WebSocket upgrade 请求支持自定义 header）。

**是否需要用户决策:** 否。

### P2-5: `sync_events` 表无自动清理机制

**文件:** `backend/src/sync.js`

**现象:** 每次内容变更都向 `sync_events` 表插入记录，表持续增长。`loadSyncPayload` 按 cursor 递增查询，旧数据不会被清理。

**风险:** 随着时间推移，表体积增大，sync 查询性能下降。存储成本增加。

**建议修法:** 加定时清理任务：

```sql
-- 删除 7 天前的 sync_events
DELETE FROM sync_events WHERE created_at < now() - interval '7 days';
```

可以用 PostgreSQL 的 `pg_cron` 扩展或用 Node.js `setInterval` 实现。

**是否需要用户决策:** 否。

### P3-2: SQL 迁移 008 缺少 down 脚本

**文件:** `backend/sql/008_post_preview_images.sql`

**现象:** `ALTER TABLE posts ADD COLUMN IF NOT EXISTS preview_image_object_keys text[]`。`IF NOT EXISTS` 保证幂等但无法回滚。

**风险:** 极低。仅当需要完全回滚数据库 schema 时才需要。MySQL/PostgreSQL 不支持 `DROP COLUMN IF EXISTS` 的原子性（需要单独写）。

**建议修法:** 如有迁移工具链，补充一个 `008_down.sql`：

```sql
ALTER TABLE posts DROP COLUMN IF EXISTS preview_image_object_keys;
```

当前手动管理模式可接受。

### P3-5: 首页图片加载无磁盘缓存

**文件:** `ZhouBianTuan/CommonComponents.swift:4-57`

**现象:** `RemoteImageLoader` 每次加载图片走网络。`URLSession` 依赖系统 HTTP 缓存，但 `configuration.requestCachePolicy = .reloadIgnoringLocalCacheData` 禁用了默认缓存。图片重新下载消耗用户流量并拖慢首页。

**风险:** 用户流量消耗大，首页图片加载慢（尤其移动网络）。

**建议修法:** 在 `RemoteImageLoader.load` 中添加基于 URL hash 的本地文件缓存：

```swift
func load(urlString: String) {
    // 1. 检查磁盘缓存
    if let cached = diskCache.image(for: urlString) {
        state = .loaded(cached)
        return
    }
    // 2. 网络加载
    // 3. 写入磁盘缓存
}
```

配合 CDN 上线后，这个问题会减轻但仍建议保留本地缓存以节省用户流量。
